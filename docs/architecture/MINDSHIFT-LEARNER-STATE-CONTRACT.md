# MindShift — Контракт состояния ученика V1

**Дата:** 31.07.2026
**Статус:** V1, действует на период закрытого пилота
**Компаньон-документ:** `docs/canon/MINDSHIFT-PRODUCT-CANON-V1.md`
**Источник истины:** `prisma/schema.prisma` (datasource `sqlite`, история миграций Prisma отсутствует — см. §8)

Документ фиксирует, где и как хранится состояние ученика, кто им владеет, что уходит во внешний AI-контур и что происходит при обрыве связи, потере кода доступа или отзыве согласия. Каждое поле процитировано по реальной схеме и реальному коду — плейсхолдеров в документе нет.

## 1. Идентичность и доступ

Один аккаунт Clerk = одна семья = один профиль ребёнка в V1. Идентификатором Clerk выступает email родителя; у самого ребёнка учётных данных нет вообще — ни пароля, ни email, ни логина, только устройство и одноразовый код.

Точка входа — одноразовый код доступа, модель `AccessCode`. Жизненный цикл: `issued` → `active` (родитель активирует ссылку: два opt-in согласия плюс привязка `clerkId` через find-or-create в Clerk) → `redeemed` (ребёнок вводит код на устройстве). Код — не одноразовый, а посемейный ключ вплоть до `expiresAt`: повторный редемпшн уже выкупленного кода не заводит новую сессию с нуля, а возвращает ТОТ ЖЕ `clerkId` без изменения состояния. Комментарий в `src/lib/access-code.ts` называет это осознанным решением, а не дырой:

> "the code is a single-ACCOUNT key, not single-use, until it expires (spec §2)"
> "Re-entry to the SAME account: no state change; the code remains the family's key until expiresAt."

Технически гарантия первого редемпшна — атомарный условный апдейт (`updateMany` с `where: { status: "active" }`): гонка двух параллельных запросов не может выкупить код дважды. Повторный redeem уже `redeemed`-кода — отдельная разрешённая ветка (сверка по `clerkId`), а не replay-атака: ребёнок с истёкшей Clerk-сессией не остаётся заблокирован только потому, что код уже был использован однажды.

Коды никогда не хранятся в сыром виде. `AccessCode.codeHash` и `AccessCode.activationTokenHash` — HMAC-SHA256 от значения с индивидуальной солью (`salt`, `activationSalt`), оба поля `@unique`. Комментарий модели в схеме: "Raw code & raw activation token are NEVER stored — only HMAC-SHA256(value, salt + CONSENT_CODE_PEPPER) digests."

COPPA-стирание (§6, `deleteChildData`) удаляет строки `AccessCode` тоже — причём не только по `clerkId`, но и по `issuedForEmail`, совпадающему с email родителя из записи согласия. Иначе "призрачный" код, выпущенный на тот же email до удаления, пережил бы стирание аккаунта и продолжал бы резолвиться на стёртую семью.

## 2. Граница согласия

`ParentalConsent` — одна строка на аккаунт (`clerkId @unique`). Правило валидности в `src/lib/consent.ts` (`hasValidConsent` / `isCurrentValidConsent`) дословно:

> "Valid consent = row exists, verifiedAt != null, serviceConsent && externalAiConsent, revokedAt == null, consentVersion current."

Согласие действительно, только если ОДНОВРЕМЕННО: строка существует, `verifiedAt` проставлен (email подтверждён шестизначным кодом), ОБА opt-in включены — `serviceConsent` (сбор/использование данных ребёнка для обучения) и `externalAiConsent` (отдельное согласие на внешний AI-контур NVIDIA/Google — email-plus сам по себе не считается достаточным раскрытием для третьей стороны), `revokedAt` пуст, и `consentVersion` совпадает с текущей константой `CONSENT_VERSION`.

`hasValidConsent()` — fail-closed резолвер: при отсутствии `clerkId` результат `false` без обращения к БД; любая ошибка БД/адаптера ловится в `catch` и тоже возвращает `false`, а не бросает исключение наружу. Это единственная точка, которую обязаны проходить все пути, трогающие данные ребёнка (`/api/chat`, lesson-chat, `/api/monster`, `/api/tts`, согласно комментарию в файле). Поднятие `consentVersion` (правки текста раскрытия или самого потока данных) автоматически переводит все старые строки в "не текущие" — родителя переспрашивают заново без ручной миграции данных.

Эффект отзыва (`revokeConsent`, ставит `revokedAt`): гейты закрываются немедленно на следующем же вызове резолвера. Ребёнок посреди сессии не видит техническую ошибку — интерфейс показывает спокойный экран "сессия завершена" и уводит на главный экран. Данные при этом НЕ удаляются — они хранятся до explicit-удаления родителем или до истечения окна хранения (см. §6).

## 3. Канонический прогресс (source of truth)

Прогресс ученика — не отдельный объект "состояние сессии", а производная от двух таблиц:

- `ConceptMastery` — по одной строке на пару (`userId`, `concept`), `@@unique([userId, concept])`: `mastery` (float), `intervalStep` (Leitner-шаг, 0 = "к повтору сейчас"), `nextReviewAt`.
- `TaskAttempt` — append-only попытки: `concept`, `family`, `tier`, `pass`, идемпотентный `eventId` (`@unique`, опционален, но при наличии дедуплицирует ретраи). Схема прямым текстом запрещает хранить реплику ребёнка: "Never stores the child's utterance (COPPA)."

Завершённость сессии — ВЫЧИСЛЯЕМАЯ величина: сессия считается пройденной, когда для всех обязательных practice- и transfer-проверок в `TaskAttempt` есть проходящая (`pass = true`) запись на требуемом `tier`. Позиция возврата внутри сессии при повторном заходе (обновление страницы, новое устройство, истёкшая Clerk-сессия) заново вычисляется из тех же попыток — не читается из отдельного "курсора". Отдельная таблица прогресса сессии документирована как ОПЦИОНАЛЬНАЯ оптимизация на будущее, не обязательная для корректности пилота — в текущей `prisma/schema.prisma` такой модели нет вовсе, и это не баг: правильность подсчёта не зависит от её существования.

`AtlasLearningSession` — исключительно advisory-аудит решений NBA-контура (`decisionId`, `decisionScore`, `masteryBefore`/`masteryAfter`, JSON-квитанции `decideReceiptJson`/`outcomeReceiptJson`); комментарий модели: "Atlas NBA session audit — decision metadata stored in VOLAURA, not Atlas." По правилу спецификации от 27.07 этот трек НИКОГДА не лежит на критическом пути ребёнка — сбой записи аудита не блокирует и не искажает прогресс, посчитанный из `ConceptMastery`/`TaskAttempt`.

## 5. Машина состояний сессии

Состояния: `возврат` → `столкновение` → `разбор` → `практика(и)` → `перенос` → `итог` → `complete`.

Переходы происходят только при прохождении детерминированной проверки. Запрос подсказки (hint) и повторная попытка НЕ меняют состояние. Событие простоя внешнего AI переводит ТЕКУЩЕЕ состояние в его детерминированный fallback (режим выбора вариантов, choice mode) без потери позиции — сессия не откатывается и не обнуляется. `итог` никогда не гейтит прохождение: он оценивается LLM только по качеству вознаграждения (reward-quality), а не как проверка на прохождение.

Инварианты:
- записанные попытки (`TaskAttempt`) никогда не теряются;
- гейты двигаются только вперёд, и только при прохождении (`pass = true`);
- состояния "провал" не существует — есть только повтор.

## 6. Восстановление (recovery-контракт)

| Ситуация | Поведение | Гарантия |
|---|---|---|
| Обновление страницы посреди сессии | позиция вычисляется заново из `TaskAttempt` | ничего не теряется |
| Смена устройства | тот же код доступа вводится заново | тот же аккаунт, весь прогресс |
| Код потерян | оператор выпускает НОВЫЙ код на тот же email родителя | find-or-create по email идемпотентен → ТОТ ЖЕ пользователь Clerk, прогресс цел |
| Истекла сессия Clerk | ребёнок заново вводит код | тот же аккаунт (см. §1, ветка "уже redeemed") |
| Согласие отозвано | спокойный экран закрытия, гейты закрыты | данные сохраняются до удаления родителем или окончания окна хранения |
| Родитель потерял доступ к email | ручная проверка личности оператором (масштаб пилота — 10 семей), решение логируется | — |
| Полное стирание, `deleteChildData` (`src/lib/child-data.ts`) | одна транзакция `prisma.$transaction`: удаляет `AccessCode` (по `clerkId` ИЛИ по `issuedForEmail` из записи согласия) → `ParentalConsent` → `ConsentVerification` → `RewardEvent`, `TaskAttempt`, `ConceptMastery`, `AtlasLearningSession` → `User.delete` (каскадом уносит `Monster`, `Inventory`, `LessonProgress` через `onDelete: Cascade`) | аккаунт Clerk НЕ удаляется — документированная в коде граница ("belongs to the parent and may be used to request access again") |
| Мягкий сброс, `restartChildData` (`src/lib/child-data.ts`) | одна транзакция: обнуляет `RewardEvent`, `TaskAttempt`, `ConceptMastery`, `AtlasLearningSession`, `Inventory`, `Monster`, `LessonProgress`; `User` сбрасывается до `xp=0, crystals=0, streak=0, activeStep=1` | `ParentalConsent` не трогается — согласие сохраняется |

`deleteChildData` и `restartChildData` целиком выполняются внутри `prisma.$transaction` — частичное стирание или частичный сброс невозможны по конструкции (либо всё, либо ничего).

## 7. Версионирование контента

Сессии — типизированные данные в git, а не записи в БД. Во время активной пилотной недели опубликованный контент допускает только fix-правки (опечатки, формулировки подсказок) — семантика проверок (check) меняться НЕ может. Ребёнок, начавший неделю, завершает её на содержимом с сохранённой семантикой; это гарантируется правилом "только аддитивно", а не персональным пиннингом контента на конкретного ученика. Персональный content pinning отложен на период после пилота.

TRIGGER: если семантику проверки необходимо изменить посреди пилота — это эскалация, а не хотфикс.

## 8. Миграции и откат

Факт: истории `prisma migrate` в проекте нет. Prisma CLI не умеет напрямую водить DDL по `libsql://`, поэтому схема применяется через `scripts/turso-db-push.mjs` — идемпотентный `CREATE TABLE IF NOT EXISTS`.

Правила V1:
1. Зафиксировать baseline SQL-снимок, сгенерированный `prisma migrate diff` (пункт волны реализации, ещё не сделано).
2. На время пилота изменения БД — ТОЛЬКО аддитивные (новые таблицы, nullable-колонки); деструктивные изменения запрещены до окончания пилота.
3. Откат кода = мгновенный откат Vercel; аддитивность схемы гарантирует, что старый код безопасно работает поверх более новой схемы.
4. Любая продовая миграция или деплой — по-прежнему требует подтверждения CEO (постоянная граница).
